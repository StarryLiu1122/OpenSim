# ADR 0003：V6 权限——对象级受限注册表与按账户授权

日期：2026-09-21。状态：已实施并经存储事务、双客户端实时收敛和重启持久性验证。应用版本 0.6.0（V6-2 阶段）。

## 背景

V5 的对象级可见性来自实例配置 `private_objects`：静态、只在启动时读取、不能运行期授予或收回，也不持久化运行期的授权决定。V6-2 要求"所有者/编辑者/观察者角色 + 对象级共享授权的授予与收回，默认拒绝"，且授权变更要在多客户端间实时收敛。V6-1 已提供持久账户/会话底座（ADR 0002）。

## 选择

| 候选 | 适用性与取舍 |
| --- | --- |
| 继续只用配置 `private_objects` | 零迁移成本，但运行期不可管理，不满足任务验收 |
| 权限写入世界 JSON（对象加字段） | 权限随世界提交走 CAS 队列，简单但授权变更与世界编辑互相阻塞，且世界格式要升版 |
| **独立注册表 + 授权表（本轮选择）** | 授权操作独立于世界写队列，立即生效；不动世界格式 3 |

具体决定：

1. **schema 5**：`restrictions(object_id PK, set_by, at_ms)` 登记受限对象；`grants(object_id, account_id, granted_by, granted_at_ms, PK(object_id,account_id))` 登记允许账户。对世界对象是**软引用**：世界每次提交整体重写 objects 表，不能建外键；对象被删除后其授权行成为惰性残留，`permit list` 以 `exists` 标记，清理由后续维护任务定义。
2. **默认拒绝**：对象进入 `restrictions` 后仅授权账户可见/可改；未受限对象保持 V5 的全体可见语义。解除限制同事务清掉该对象全部授权。
3. **防自锁**：执行限制的账户自动获得该对象的授权，避免所有者把自己锁在对象外。
4. **授权者资格**：owner 角色可管理任何对象；非 owner 只能管理 `owner_id` 等于自己 `actor_id` 的对象；observer 一律不能管理（只读语义延伸到授权面）。
5. **配置播种**：`config.private_objects` 只在注册表为空记录时落库一次（以 owner 账户署名），之后以数据库为准；删除配置不影响已持久授权。
6. **实时收敛**：可见性变化不需要专门推送——每 50 ms 的投影差异自然把新可见对象作为 upsert、新隐藏对象作为 delete 分发给各客户端；资产目录（`_publish_assets`）在每次授权变更后重算，私有资产的 HTTPS 允许列表同步收紧。
7. **组语义沿用 V5**：组内任一成员不可见则整组不投影；限制一个成员即对未授权者隐藏整组。

## 后果与退出路径

- 授权操作是独立存储事务，不经过世界 CAS 队列；授权与世界编辑并发时各自有序，互不阻塞。
- `permit` 包沿用 fp 0.3 能力扩展方式（同 ADR 0002 第 4 条），回复 `permit_result`。
- 越权变更返回结构化 `PERMISSION_DENIED`，世界修订不变（有测试断言）。
- 惰性授权残留（对象已删）不影响正确性：可见性判断只针对世界中存在的对象。批量清未提交对象的授权行属于后续维护项。
- 未来对象级"所有权转移"可在 `grants` 之上加 owner 语义；当前对象 `owner_id` 仍是领域 actor，未改。
