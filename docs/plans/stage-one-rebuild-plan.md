# OpenSim 第一阶段实施计划

日期：2026-09-14

分支：`codex/stage-one-rebuild-plan`

状态：待实施；本次提交只包含计划和 README，不包含原型实现。

先理解 OpenSim 的数据与运行机制，以一个 256×256 米区域为边界，用现代游戏引擎复现可验证的基础功能。按“原版行为基线 → 数据契约 → 单区域 → 持久化 → 多人同步 → 权限与交互”推进，给后续大模型和智能体留下稳定的世界操作接口。

## 1. 范围与交付目标

**首个可交付成果（M0—M4）：一个能进入、能编辑、能保存并恢复的单区域原型，以及它与 OpenSim 数据结构的对应说明。**

**第一阶段原型验收（M0—M7）：在此基础上，实现两个客户端、服务端裁定、最小身份和物体归属、资产/库存引用及一个内置交互行为。**

本阶段包含：

- 理解区域、地形、物体、资产、库存、物理与存储调用链。
- 建立独立的原 OpenSim 测试实例，保存行为基线和测试世界。
- 验证现代引擎、模块边界、版本管理、保存恢复与网络同步方案。
- 实现数据接口、日志、测试场景和可重复启动流程。

后续专题：完整 LSL/OSSL 兼容、已有脚本状态迁移、Firestorm 连接新服务器、完整用户与资产权限体系、复杂连体物体、地块/庄园、跨区域和 Hypergrid、无人机/CAD/BIM 导入、真实大模型服务、城市级规模优化。

延期项目必须进入功能覆盖表，标注“未实现”和影响。第一阶段原型通过不能称为完整替代 OpenSim。本计划按一个执行主体安排任务，不划分人员职责；里程碑按验收推进，工期根据实测调整。

## 2. 已知基线和关键认识

- 固定上游提交为 `1f4a6dd1d3ff653ecc2748a7764106c30ac4ef9d`，来源和校验见 [UPSTREAM.md](../UPSTREAM.md)。[prebuild.xml](../../prebuild.xml) 的目标为 `net8_0`。
- 当前尚未完成该源码快照的首次编译和运行。已有安装包的结果需要记录版本，不能自动作为本快照的编译验证。
- 当前重点是数据理解和现代引擎功能复现；早期 [C#/.NET 指南](../opensimulator-stage-one-refactoring-guide.docx) 保留为维护与兼容性参考。
- C# 是语言，Godot 是引擎，Python 常用于服务与工具；它们不是同一层面的替换关系。先确定职责，再决定语言。
- 256×256 米是首个测试范围，区域尺寸保留为字段。[RegionInfo.cs](../../OpenSim/Framework/RegionInfo.cs) 本身包含尺寸设置。
- 地形网格、可见模型、碰撞形状、物体实例、资产内容、库存引用和脚本状态分别建模。

## 3. 候选软件栈与选择关口

以下为待验证方案，不表示已经安装、集成或通过测试。

| 职责 | 首选验证方案 | 选择条件 |
| --- | --- | --- |
| 客户端、场景与交互 | Godot 4 + 带类型标注的 GDScript | 通过地形、角色、物体、碰撞和导出验证后固定版本 |
| 区域模拟 | Godot 无界面服务端 | 从相同世界数据启动，服务端拥有最终状态 |
| 物理后端 | 验证 Godot 的 Jolt 后端 | 测试角色、地形、刚体与无界面运行；不承诺旧引擎轨迹完全一致 |
| 存储 | 先版本化 JSON 快照，随后接 PostgreSQL | 快照验证序列化语义；数据库验证事务、迁移、备份与恢复 |
| 平台与持久化接口 | Python + FastAPI | M4 引入，不在每个物理帧发 HTTP 请求 |
| 既有服务 | C# 参考实现或按需保留的独立服务 | 复用收益明确且可隔离时保留，记录依赖维护方案 |
| 性能扩展 | 按需评估 C++ | 实测确认具体热点后才立项 |
| AI 辅助开发 | 参考 GameFactory-3A | 固定参考提交，在隔离样例验证后决定是否引入代码 |

Godot 支持无界面运行与专用服务器导出；同步、身份权限、持久化仍需本项目实现。其多人网络接口是候选传输方案，不提供 Firestorm 兼容。[专用服务器文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html)、[多人网络文档](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)、[Jolt 文档](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)。

FastAPI 与 PostgreSQL 的组合是本项目提案，需验证取消、并发、事务和迁移；驱动、迁移库及版本在 M4 决策记录中固定。[FastAPI 文档](https://fastapi.tiangolo.com/)、[PostgreSQL 文档](https://www.postgresql.org/docs/current/tutorial.html)。

记录引擎精确版本、匹配的导出模板、插件/参考代码提交、Python 与数据库版本。固定依赖，升级前跑回归。M2 失败时先定位能力缺口，再决定替换版本、模块或引擎。

## 4. 源码阅读顺序与数据对应

每行产出：字段含义、单位与坐标、创建/更新/删除流程、状态归属、保存位置、新原型对应结构和未覆盖行为。

| 阅读对象 | 原版入口 | 重点问题 | 建议概念 |
| --- | --- | --- | --- |
| 区域 | [RegionInfo](../../OpenSim/Framework/RegionInfo.cs)、[RegionSettings](../../OpenSim/Framework/RegionSettings.cs) | ID、尺寸、位置与地形设置如何关联？ | RegionDefinition |
| 地形 | [TerrainData](../../OpenSim/Framework/TerrainData.cs) | 采样、插值、修改标记和存储格式如何工作？ | HeightField |
| 世界容器 | [Scene](../../OpenSim/Region/Framework/Scenes/Scene.cs) | 对象、角色、模块与模拟如何组织？ | RegionRuntime |
| 物体 | [SceneObjectGroup](../../OpenSim/Region/Framework/Scenes/SceneObjectGroup.cs)、[SceneObjectPart](../../OpenSim/Region/Framework/Scenes/SceneObjectPart.cs) | 实例、整体/局部变换、材质、归属、形状和物理标记是什么？ | WorldObject / ObjectPart |
| 角色 | [ScenePresence](../../OpenSim/Region/Framework/Scenes/ScenePresence.cs) | 用户、连接、角色如何关联和解绑？ | Participant / AvatarState |
| 资产与库存 | [AssetBase](../../OpenSim/Framework/AssetBase.cs)、[InventoryItemBase](../../OpenSim/Framework/InventoryItemBase.cs)、[TaskInventoryItem](../../OpenSim/Framework/TaskInventoryItem.cs) | 资产 ID、条目 ID、所有者、父物体分别是什么？ | AssetRecord / InventoryEntry |
| 物理 | [PhysicsScene](../../OpenSim/Region/PhysicsModules/SharedBase/PhysicsScene.cs) | 地形、碰撞体、步进和回调怎样与 Scene 对接？ | PhysicsAdapter |
| 存储 | [ISimulationDataStore](../../OpenSim/Region/Framework/Interfaces/ISimulationDataStore.cs)、[Data 实现](../../OpenSim/Data/) | 对象、库存、地形、区域设置如何写入和恢复？ | WorldRepository |
| 脚本 | [SceneObjectPartInventory](../../OpenSim/Region/Framework/Scenes/SceneObjectPartInventory.cs)、[脚本引擎](../../OpenSim/Region/ScriptEngine/) | 脚本资产、实例、事件和运行状态怎样关联？ | BehaviorDefinition / BehaviorState |

一个已核实的边界：`ISimulationDataStore.StoreObject` 的说明明确不包含库存，库存由 `StorePrimInventory` 单独处理。不能用“保存一个物体 JSON”就声称完整保存了 OpenSim 物体。

先跟踪完整调用链：创建方块 → 修改位置/材质 → 保存 → 退出 → 重启恢复。再增加库存与简单交互，避免只阅读类名。

## 5. 建议模块与接口边界

以下目录为后续建议，当前提交只创建计划文档。

```text
prototype/
  godot/                 客户端与无界面服务端项目
    domain/              区域、物体和命令，减少对渲染节点的依赖
    adapters/            数据到场景、碰撞和网络的转换
    client/              画面、输入、选择和编辑
    server/              命令校验、区域状态与同步
    tests/               自动化功能场景
  services/world_api/    M4 起评估的 HTTP 与持久化服务
  contracts/             版本化数据、命令、有效/无效样例
  fixtures/              小型世界、程序生成资产、快照
docs/
  architecture/          数据对应表、调用链、架构决策
  verification/          启动步骤、环境、结果、限制
```

- 物体使用稳定 ID；Godot NodePath 或临时实例编号仅作为运行时映射，不作为持久化主键。
- 区域保存尺寸、原点、单位、采样间距和版本。256 米边长与高度样本数量分别定义，明确边缘和网格顶点规则。
- 固定坐标约定，单独实现 OpenSim 与引擎的位置、方向和旋转转换，以已知位置/朝向做往返验证。
- 资产描述内容与类型，物体引用资产，库存条目有自身 ID、资产引用和归属。未来生成资源走相同入口。
- 首批命令为 `GetRegionSnapshot`、`CreateObject`、`UpdateObjectTransform`、`UpdateObjectAppearance`、`DeleteObject`、`SaveRegion`。具体参数在 M1/M3 固定，不表示现成 API 已存在。
- 命令包含请求 ID、区域/对象、预期修订、参数与格式版本；调用身份来自已验证会话，不信任客户端声明的所有者。
- 服务端先验证参数、身份、权限、修订和重复请求，再修改世界并广播。结果包含成功/失败、请求 ID、新修订与错误码。
- M3 本地原型也通过命令入口修改数据；M5 后客户端提交意图，服务端裁定最终状态。
- 高频模拟留在区域进程；存储和外部调用不阻塞物理循环。明确一致快照、写入顺序、重试与“已保存”确认时机。

## 6. 分步任务与验收

### M0：建立原版基线

- [ ] 固定源码，记录 SDK、Viewer、数据库、物理后端、操作系统和托管/原生依赖。
- [ ] 按 [BUILDING.md](../../BUILDING.md) 在独立副本生成工程、编译和启动单区域。保存命令、日志与失败原因。
- [ ] 用 Firestorm 验证登录、移动、建方块、改属性、保存恢复和简单脚本，记录输入、结果与截图/录像。
- [ ] 保存可恢复的测试世界，使用独立配置、端口、数据库和测试账户。

**交付：** 基线说明、行为用例表、环境清单与不含凭据的最小测试数据。

**通过条件：** 可按说明重复启动和恢复，每个基线用例有结果。若暂用安装包观察，与“源码编译成功”分别标记。

### M1：明确数据模型与覆盖范围

- [ ] 完成第 4 节对应表及方块创建、保存、加载调用链。
- [ ] 定义区域、地形、物体、资产、库存、参与者的最小字段和引用。
- [ ] 固定坐标、单位、UUID、旋转、尺寸和高程规则，准备有效样例与缺字段、坏引用、越界等无效样例。
- [ ] 建立覆盖表，标记“直接复用 / 本期复现 / 简化实现 / 后续实现”。

**交付：** 数据字典、格式 v1 草案、样例和覆盖表。

**通过条件：** 能解释资源引用到实例再到存储的全过程，明确简化内容；不将场景文件直接当作完整平台数据库。

### M2：验证引擎和工程骨架

- [ ] 固定 Godot、导出模板和物理后端，建立客户端与无界面服务端启动入口。
- [ ] 验证角色、碰撞、无界面加载与日志，记录实际命令。
- [ ] 在隔离样例评估 GameFactory 的项目创建、资源注册、运行和验证，记录参考提交与原生执行结果。
- [ ] 写选型决策，说明接口思想、复用代码、未验证能力与替代条件。

**交付：** 可启动骨架、版本记录、启动说明和决策记录。

**通过条件：** 干净检出可以导入和启动，服务端不依赖可见窗口。GameFactory 失败时可继续使用原生入口，不让可选工具阻塞核心工作。

### M3：完成单区域和物体操作

- [ ] 加载一个 256×256 米区域和简单高度场，显示材质并生成碰撞体。
- [ ] 加入角色移动、视角和区域边界处理，禁止掉出地面或无提示越界。
- [ ] 通过命令创建、选择、移动、旋转、缩放、改色、删除基础方块，赋予稳定 ID。
- [ ] 分离逻辑数据、可见模型与碰撞形状，验证变换后三者一致。

**交付：** 单区域演示、固定小场景、物体操作接口和说明。

**通过条件：** 完整操作流程通过；区域边缘、非法尺寸、未知 ID 和重复删除有明确结果。先支持方块，复杂网格和连体物体单列后续项。

### M4：完成持久化与恢复

- [ ] 实现版本化快照，保存地形、对象 ID、变换、材质、资产引用与归属；标明暂不保存的运行时状态。
- [ ] 验证文件写入失败和损坏快照不会覆盖最后有效版本，完成正常关闭后的保存/加载往返。
- [ ] 引入 PostgreSQL 最小表与迁移：区域、对象、资产元数据、最小身份/归属；为 M6 库存预留明确引用关系。
- [ ] 通过独立持久化服务提交一致快照，定义事务、并发修订与保存确认；资产文件放独立目录，数据库保存引用、类型和校验信息。
- [ ] 验证数据库不可用、未知版本、缺失资产、重复 ID、进程重启与备份恢复。

**交付：** 快照格式、建库/迁移步骤、持久化接口、备份恢复说明和首个可持久化原型。

**通过条件：** 收到“保存成功”后，重启恢复同一批 ID 和属性；失败明确报错并保留最后有效快照。基础浮点属性往返误差暂定不超过 `1e-4`（按字段单位）；物理轨迹另做行为测试，不要求逐帧一致。

### M5：完成双客户端与服务端裁定

- [ ] 启动一个服务端和两个客户端，服务端管理对象生命周期和修订号。
- [ ] 同步角色、创建、变换、删除，处理迟加入时初始快照与更新衔接。
- [ ] 编辑采用预期修订号检查；冲突明确拒绝并返回当前版本，不静默覆盖。
- [ ] 按会话和请求 ID 去重，绑定服务端身份，限制未授权编辑。
- [ ] 验证断线重连、延迟、丢包与重复请求，不重复生成或复活已删除物体。

**交付：** 双客户端演示、网络契约和冲突/重连测试。

**通过条件：** 操作结束后两端 ID、修订和属性一致。局域网受控测试暂以 1 秒内最终状态一致为目标；另记录 100 毫秒延迟、1% 丢包场景结果。这些是验收目标，不是已测性能。

### M6：完成最小归属、库存与交互

- [ ] 使用两个测试身份验证“可查看、仅所有者可编辑”，记录登录验证方式；开放部署前另做正式身份方案。
- [ ] 为物体关联一个资产和一个库存条目，分别使用稳定 ID，验证保存恢复后的引用。
- [ ] 实现服务端内置 `Touch → ChangeColor`，经命令和权限入口执行并同步。
- [ ] 定义行为参数与持久化状态，记录与 LSL/OSSL 的对应关系及缺失语义。

**交付：** 权限规则、资产/库存样例、交互演示和恢复测试。

**通过条件：** 第二个身份不能编辑别人的物体；允许的交互在两端一致；重启后归属与引用不丢失。内置行为不等于 LSL/OSSL 兼容，也不开放任意上传脚本执行。

### M7：完成工程与回归验收

- [ ] 在独立环境验证检出、依赖准备、导入、服务启动、迁移、客户端运行与恢复。
- [ ] 将契约、保存恢复、权限、双客户端关键路径接入可运行的自动化检查，补充人工交互记录。
- [ ] 记录硬件和分辨率，以 2 个客户端、100 个静态物体、10 个动态物体运行 30 分钟，记录帧率、模拟耗时、内存、网络与错误；此为初始负载，不代表容量。
- [ ] 完成覆盖表与问题清单，优先修复丢数据、越权、状态分歧和无法复现的问题。
- [ ] 用确定性程序调用查询/动作接口，验证未来智能体入口及失败、超时、重复动作反馈。

**交付：** 可复现原型、验证报告、演示、架构决策和剩余任务。

**通过条件：** M0—M6 用例通过，无未解决的数据丢失、越权或持续状态分歧；性能与限制如实记录。之后再评估完整脚本、资产权限、跨区域和模型接入。

## 7. 第一周从哪里开始

每天约一个可交付任务，遇到实际问题顺延，不以天数代替验收。

| 顺序 | 任务 | 可检查的结果 |
| --- | --- | --- |
| 1 | 核实版本，构建独立测试实例 | 成功日志或可定位问题清单，原版启动步骤 |
| 2 | 跟踪方块创建、修改和保存 | 类、字段、存储调用与原版操作录像 |
| 3 | 定义区域、地形和物体草案 | 可解释的世界样例及坐标/单位/ID 说明 |
| 4 | 固定 Godot，启动最小场景 | 平面、方块、角色、碰撞与无界面启动结果 |
| 5 | 通过命令创建/移动方块，做快照恢复实验 | 重启后同 ID、同位置的方块与差异记录 |

第 5 项是提前验证风险的小实验，不代表完成 M4 数据库里程碑。若 M0 未通过，记录原因；独立样例可继续探索，但不能声称完成原版功能对照验收。

- 借鉴统一结果、引擎适配、资产注册和原生验证；世界接口按 OpenSim 语义自行设计。
- 借鉴“运行、操作、记录、修正”，以保存恢复、权限和同步用例补充编译与视觉检查。
- 模型、任务、批处理分层及 CPU 替代模型契约检查，可用于后续工具开发；不能代替真实模型与游戏功能验证。
- 文档当前示例锁定 Godot `4.5.1-stable`。复用时先固定参考提交和已验证组合，再评估升级，不假设任意 Godot 4 版本兼容。
- 部分会话操作允许无引擎响应时退回本地记录；实际交互测试须要求运行时确认，例如相应接口的 `require_runtime=True`，并检查真实引擎状态。
- World 包和会话注册不等于区域数据库与多人服务器。首期不依赖付费模型、模型权重或资产生成链。

以上来自文档调研，本机可运行性、兼容性、性能及安全边界尚未验证。

## 9. 风险与处理

| 风险 | 处理与验证 |
| --- | --- |
| 只有画面，没有平台语义 | 每项同时检查数据、归属、持久化和客户端表现 |
| 坐标和物理差异 | 固定转换，测试朝向、斜坡、落地、碰撞，记录允许差异 |
| 混淆资产、实例、库存和脚本 | 分别定义 ID 与生命周期，用坏引用和重启验证 |
| 保存成功却未持久化或快照不一致 | 定义事务与确认时机，注入写入失败 |
| 越权、并发覆盖或重复执行 | 服务端验证会话、权限、修订，去重并测试重连 |
| 误以为兼容 Firestorm 和全部旧脚本 | README、覆盖表、演示明确支持范围 |
| AI 生成代码但无法解释逻辑 | 小变更关联原版行为与用例，阅读差异并保留验证证据 |
| 工具漂移和第三方成本 | 固定版本与提交，记录许可证，可选工具不阻塞原生路线 |
| 同时引入过多引擎、语言与服务 | 先单引擎单区域，M4 再接数据库服务，实测后扩展 |
