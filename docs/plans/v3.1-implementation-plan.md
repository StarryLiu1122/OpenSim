# V3.1 实施方案与交付清单

版本：0.3.1。更新日期：2026-09-15。分支：`codex/region-lab-v3-1`。

## 1. 目标

V3.1 将单区域原型扩展为可制作和复用场景内容的编辑环境。围绕建筑与家具，完成“组织部件—整体编辑—导入网格—重复放置—保存恢复”的流程，并建立后续性能优化的测量依据。

本版本继续采用 Godot 4.5.1 标准版、Jolt 和 GDScript。原版 C# 源码作为语义参考保留。暂不引入新的服务框架、数据库或在线大模型，避免在数据关系尚未稳定时同时调整运行架构。

## 2. 实施顺序与验收

| 顺序 | 工作内容 | 主要实现 | 验收结果 |
| --- | --- | --- | --- |
| 1 | 固定组合的数据契约，补齐旧存档迁移 | WorldSchema、SchemaV2、WorldTransforms | 格式 1/2 均先验证后升级；保留 ID、地形、环境与修订 |
| 2 | 实现组合命令与原子校验 | GroupCommands、WorldModel、WorldService | 建组、变换、复制、解除、删除；非法编辑保持世界与历史不变 |
| 3 | 接入编辑器和物理投影 | GroupPanel、EditorUI、WorldView | Ctrl 多选；展馆 15 个部件整体编辑；变换后的门仍可独立开关 |
| 4 | 实现有明确边界的静态资产入口 | GlbReader、MeshAssets、MeshView、AssetPanel | GLB 结构、引用、大小及几何校验；资产内容与实例分离 |
| 5 | 提供可再分发样本与可搬移存档 | fixtures/meshes、SnapshotRepository | 建筑、长凳、树；源文件删除后，存档在另一进程恢复几何与组合 |
| 6 | 建立渲染与性能基线 | 原生/UI 测试、benchmark.gd | 实际输入与 Jolt 检查；固定日景与夜景工作负载输出帧间隔和资源监测 |

代码与测试入口见 [架构文档](../../prototype/docs/architecture-and-api.md)，执行结果见 [验证记录](../../prototype/docs/verification.md)。检查项必须以对应行为和报告为依据，不能仅凭界面截图判断保存或碰撞正确。

## 3. 组合模型的取舍

组合是一层根部件与子部件关系，不支持嵌套。组记录保存区域内坐标、旋转与统一缩放；成员保存相对坐标、相对旋转和局部尺寸。对象检查器继续显示世界坐标，命令层负责转换后存储。

使用统一缩放是为了避免非均匀缩放叠加旋转产生剪切，保证世界变换、编辑尺寸与碰撞一致。组倍率允许 0.1–10，但最终每个成员仍须满足 0.2–32 米尺寸与区域边界；例如薄地板会限制整栋建筑的最小倍率。

根部件的位移与旋转由组合面板控制。删除成员前需解除组合；删除整个组合必须使用组删除操作。整体复制产生新的组及成员 ID，复用原资产内容，复制门灯状态。建立、解除组合均保留已有部件 ID。

示例展馆以地板为根，包含墙体、门、屋顶、檐廊及室内陈设，共 15 个部件。现有存档不会自动按名称推断组合，防止错误关联用户内容。

## 4. 资产入口与真实感

首个入口限定为静态 GLB 2.0，支持三角形网格、不透明 PBR 基础参数与内嵌 PNG 基础色贴图。模型按米制导出；导入时将节点变换烘入几何，实例定位点统一为可见包围盒中心。完整支持范围见 [组合与资产规范](../../prototype/docs/groups-and-assets.md)。

碰撞可使用名称以 `COL_` 开头的节点。若提供代理，则只用代理碰撞；否则用可见网格生成静态三角碰撞。可进入建筑需要明确保留入口和内部空间，不能以一个包围盒替代所有墙体。

V3.1 的三个原始样本用于验证结构和流程，采用 CC0-1.0；不属于真实城市扫描或高精度写实资产。后续真实感提升应依次验收真实尺寸、可达空间、正确碰撞、材质和光照，再增加资产数量。

资产以完整 SHA256 标识内容，原始 GLB 内嵌于快照。同一内容重复导入复用记录；多实例共享资产身份。采用内嵌方案便于原型阶段搬移和检查，代价是 JSON 体积与保存开销增大。下一阶段存储设计应将资产二进制外置，保留摘要校验与可独立恢复的导出包。

## 5. 测试要求

| 范围 | 重点失效情况 |
| --- | --- |
| 组合 | 重复或不存在的成员、跨归属、失效根部件、越界、零倍率、非法四元数、变换后碰撞偏移 |
| 资产 | 外部依赖、循环节点、非法访问器范围、过量几何、不支持的通道、内容摘要不符、资产被引用时移除 |
| 存储 | 旧格式误判、迁移隐式改写、资产源文件丢失、移动路径、重启后内存缓存为空 |
| 界面 | 多选丢失、根坐标被误当局部坐标、导入成功却未能创建实例、只改显示而未保存 |
| 物理 | 组合旋转缩放后门洞偏移、GLB 入口被代理封闭、角色穿墙或无法落在室内地板 |

测试使用独立目录。以包含空格的新目录重新安装固定引擎，并先执行首次启动，再执行完整测试，避免现有导入缓存掩盖依赖问题。

## 6. 性能记录与优化次序

采用两个固定工作负载：43 对象的日间展馆、增加 200 个网格实例的夜间场景。固定相机、1280×720 分辨率及太阳时刻；预热至少 2 秒、90 帧，采样至少 3 秒、180 帧。保留原始帧间隔、P50/P95、场景构建至首帧时间、绘制调用及 Godot 内部静态内存。

测量结果只用于相同硬件和设置下的版本比较。夜景与日景光照负载不同，不能用两者帧率直接推导“每新增对象的成本”。500 对象是输入限制，并非已验证容量。

优化优先级依据实测热点确定：复用 Mesh/Material 资源与实例批处理；按需减少阴影灯光；局部更新与空间索引；再评估 LOD、地形分块和渲染器升级。V3.1 不提前引入这些机制。

## 7. 下一轮工作的开始位置

2026-09-16 补充：本节保留 V3.1 交付时的后续事项。结合老师提供的两份指导文档，现行顺序已细化为“原版对照与契约 → 最小融合网关 → 数据库”，并增加 Web 导出预验证；执行以 [V4 实施计划](v4-implementation-plan.md) 和 [总体路线](stage-one-rebuild-plan.md) 为准。

1. **建立原版行为对照。** 独立构建固定版本 OpenSim，以两个部件组成的物体为最小案例，记录根部件、局部坐标、复制、解除组合和重启恢复。将结果补入数据对应表。
2. **整理存储接口。** 在现有 JSON 实现之外定义区域、组合、成员和资产仓储契约；明确事务边界、迁移规则、二进制存放方式及快照导出格式，再选择数据库与服务端框架。
3. **补充一个真实授权资产。** 选择尺寸和许可明确的小建筑，在当前 GLB 限制内完成导出、碰撞代理制作、导入和通行验收，记录不支持项，不同时扩展 CAD、无人机、OAR 三条路径。

上述任务完成后进入 V4 的数据库实现。多人同步、身份库存、智能体分别在后续版本推进，整体路线见 [版本计划](stage-one-rebuild-plan.md)。
